Timeboxed design assessment

Assetpro

An asset and inventory management system covering the full lifecycle — requisition to retirement — designed against a fixed brief and a hard deadline.

At a glance
RoleSole designer
ContextAssessment for a management consultancy
ToolFigma, working prototype
DateApril 2025
The brief

Nine modules, one deadline. The first design problem was deciding which parts of the product actually carried it.

A consultancy's client needed an asset and inventory management system. Organisations in that position share the same failures: no full picture of what they own, no reliable read on whether it still works, no trace of an asset's life from requisition to retirement, and depreciation tracked somewhere nobody looks.

The brief named nine modules and asked for a prototyped, working interface. Designing all nine shallowly would have produced a convincing screenshot and an unusable product, so I built a system deep enough to be judged and left the rest represented rather than invented.

The problem

An asset register looks like a table with an add button. It isn't. An asset moves through states — requested, approved, procured, tagged, assigned, maintained, depreciating, retired — and a different person with different permissions touches it at nearly every one.

That's what breaks the table model. The procurement officer and the person receiving a laptop are looking at the same record and need almost nothing in common from it. Design the list well and you've still designed nothing, because the value is in the transitions between states, not the rows.

Decisions
  • Design the system before the screens. I built the design system first, so components stayed consistent across a product too large to hand-style. On a fixed deadline this buys back more time than it costs.
  • Anchor on lifecycle, not inventory. The asset page is organised around where an asset is in its life rather than its category, which makes state changes the primary action instead of something buried in an edit form.
  • Permissions as structure, not a settings page. Role-based access shapes what the request manager shows each person, so compliance is a property of the interface rather than a policy document nobody reads.
  • Barcode and stock thresholds over manual counting. Scanning handles identification and threshold alerts handle the watching, which removes the two tasks people silently stop doing.
  • Integration points named explicitly — barcode scanners and accounting software — because an asset system that doesn't reach the tools already in use becomes a second set of numbers to reconcile.
What I'd do differently

Two or three sentences. With the deadline gone, what would you change? This section is where an assessment beats client work — you can be candid because nothing shipped and no client is reading. It's also the strongest signal of seniority on the whole site.

Outcome

Submitted as a working Figma prototype covering the end-to-end flow from requisition to retirement.
